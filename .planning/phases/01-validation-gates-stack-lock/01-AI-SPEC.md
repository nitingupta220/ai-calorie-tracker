## 1. System Classification

**System Type:** **Hybrid** — Structured Extraction (vision → dish + portion + macros) + Grounded Content Generation (advice from last-3-day meal log). Not RAG (no vector retrieval — SQL lookup on user's recent meals), not agentic (no tool-calling, no multi-step plans), not conversational (single-turn per meal, no threading).

**Description:**
A two-stage AI pipeline for urban Indian youth (18-30) using the AI Personal Coach mobile app. **Stage 1 (Vision Extraction):** user photographs an Indian meal → Gemini 2.5 Flash identifies the dish from a 50-dish pan-Indian whitelist + estimates portion in grams + emits per-item confidence; output is validated against a Pydantic schema. **Stage 2 (Dish Decomposition + Macros):** identified dish → deterministic SQL lookup into a founder-curated `dish_decomposition.json` table → maps to IFCT 2017 raw-ingredient macros → aggregates calories/protein/carbs/fat. **Stage 3 (Grounded Advice):** in parallel with Stage 2, an advice LLM (Groq Llama 3.3 70B primary) receives `{goal, target_macros, last-3-day meal log, day-so-far totals, budget bucket, veg/non-veg, current dish, ₹/gram veg-protein reference table}` and emits 1-2 sentence advice that must pass a server-side 4/4 rubric before render. Macros + advice return in a single API response within 8s P95. "Good" looks like: ≥75% dish-name match on real Indian meals (post-alpha), ≥75% advice 4/4-rubric pass rate, cost ≤₹15/active-user/month, and zero PII leaving the system.

**Critical Failure Modes:**
1. **Vision returns wrong dish or fabricated macros** — user trusts incorrect numbers, breaks core value (meal tracked wrong → advice grounded in wrong data → snowball error). Mitigated by stratified Gate 0a benchmark (≥70% dish-name + ≥60% macros within ±35%), Pydantic schema validation, two-step pipeline (no LLM math on macros — IFCT lookup is deterministic), confidence-gated UI (>3 items or conf<0.6 → user-confirm before lock).
2. **Generic advice ("eat more protein") that doesn't reference user log** — moat collapse, indistinguishable from HealthifyMe Ria, churn. Mitigated by server-side 4/4 rubric validator that REJECTS advice missing (specific food + quantity + ₹ cost + recent-log reference), single retry, then per-dish hand-written template fallback. WoZ QA Gate (≥35 founder-written examples, ≥70% AI-vs-WoZ match) BEFORE alpha goes live.
3. **PII or PHI exposed to LLM providers** — DPDP violation, ₹250 crore fine ceiling. Mitigated by strict prompt construction discipline: no name, no phone, no exact birthdate; only de-identified `user_id` + goal/macros/diet preference fields. Lint rule in CI prevents user table joins in advice-prompt-construction code.
4. **Provider rate limits / pricing change wipes economics** — single-vendor exposure breaks bootstrap. Mitigated by `ai_provider.py` abstraction with 429-fallback chain (Gemini free → OpenRouter free → paid) verified before Phase 2 ships; per-call cost log persisted; lint rule prevents provider SDK imports outside `providers/`.
5. **Advice promotes unsafe / medical claim ("eat X to cure Y")** — CDSCO + ASCI violation, Play Store rejection. Mitigated by banned-words lint check on prompt outputs + persistent CDSCO/ASCI disclaimer on every advice card + medical-niche users explicitly out-of-scope V1.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Indian consumer health & nutrition coaching (sports-nutrition-adjacent, explicitly **fitness-not-medical** — trainer-replacement positioning at ₹299/mo vs ₹3,000/mo human trainer). NOT clinical medicine, NOT registered-dietitian practice, NOT pre-diabetic / PCOS / chronic-disease management (those are V2+, CDSCO territory).

**User Population:** Urban Indian youth, age 18-30, tier-1 / tier-2 cities, gym-going or gym-curious, English/Hinglish-comfortable, ~70% vegetarian-default with non-veg option, ₹100-250/day food budget, ₹299-499/mo app-spend willingness, V1 muscle-gain goal only. Eats predominantly home-cooked Indian food (dal/sabzi/roti/rice/paneer/curd) interleaved with gym-bro staples (eggs, peanut butter, chicken, oats) and occasional restaurant/biryani meals. Pulled into the category by "calorie tracking on Indian Instagram" trend; bounces between HealthifyMe / Cult.fit / Cal AI without retaining because no incumbent grounds advice in their actual recent meals + Indian-staple cost reality.

**Stakes Level:** **Medium.** Not life-threatening (not insulin dosing, not allergy management, not chronic-disease management). Bad output causes **wrong macros logged → trajectory drift over weeks (under-eating protein → muscle-gain stalls; over-eating fat → fat-gain not muscle-gain) → trust collapse → churn**. Upper-bound stakes elevate to **High** the moment advice strays into medical territory ("eat X to manage your sugar" → CDSCO SaMD classification risk → app takedown). Lower-bound stakes are **never Low** because users are spending real money on food based on the recommendation — a ₹300/day budget user told to "add 100g paneer" is being told to spend ₹40, and bad budget advice compounds financially over a month.

**Output Consequence:** User reads macros + 1-2 sentence advice on the meal card → eats based on it → spends ₹ on the recommended food → either closes a real protein gap (good) or wastes ₹ on a Western-pattern recommendation that doesn't fit their kitchen (bad) → over 14-30 days the cumulative effect lands as muscle-gain progress OR plateau OR fat-gain. Downstream: app trust + retention + paid-tier conversion (Phase 3 ₹299/mo) + word-of-mouth in gym networks + (rarely) social-media call-out if advice is visibly wrong on a public Indian dish. **Regulatory downstream:** advice that contains "treat / cure / diagnose / manage [disease]" tokens triggers CDSCO Medical Devices Rules 2017 classification risk and ASCI Code 2023 substantiation requirement.

### What Domain Experts Evaluate Against

**Dimension: Macro accuracy on cooked Indian dishes (not raw-ingredient lookup)**
Good (expert accepts): For paneer butter masala at a stated portion (e.g. 200g), reported kcal is within ±20% of NIN/IFCT-derived cooked-dish ground truth (paneer + tomato + cashew + butter + cream + oil aggregated), protein within ±15%. Pipeline visibly decomposes the dish into recognizable Indian ingredients rather than treating it as a single opaque item.
Bad (expert flags): Reports the dish as "paneer 200g" macros (265 kcal) when the cooked dish is 450+ kcal/100g — i.e. ignored the 30g butter + 15g cashew + cream + oil load. Common in apps that hit IFCT 2017 directly without a decomposition layer.
Stakes: Critical (Pitfall 3 in PITFALLS.md — systematic 40-70% underreporting on every fat-heavy curry).
Source: IFCT 2017 (NIN/ICMR) scope — 528 raw foods, no cooked-dish entries; National Institute of Nutrition cooked-recipe sets cover ~100 Indian dishes used as ground truth; Indian sports nutritionists routinely critique apps that "report paneer when you ate paneer butter masala".

**Dimension: Vegetarian protein math grounded in ISSN 2024 + Indian-staple gram-counts**
Good (expert accepts): For a muscle-gain user at 70kg, target is 1.6-2.2 g/kg/day (i.e. 112-154 g protein); V1 default 1.8 g/kg = 126g. Advice references the gap from this target using actual Indian protein staples with correct gram-protein values: paneer ~18g/100g, soya chunks dry ~52g/100g, cooked dal ~7-9g/100g, eggs ~6g each, curd ~3g/100g, roasted chana ~18g/100g.
Bad (expert flags): Inflated target (3 g/kg) repeated as gospel from bro-science forums; OR uses wrong gram-protein density (claims dal is 15g protein/100g cooked — that is the dry/raw value, not cooked); OR ignores the fact that an average Indian thali day yields only 40-60g protein vs the 112-154g target — i.e. the advice doesn't surface the magnitude of the gap.
Stakes: Critical (Pitfall 20 — wrong target = entire advice loop misfires; moat collapse).
Source: ISSN Position Stand on Protein 2017 updated 2024 (1.6-2.2 g/kg for muscle gain resistance-trained); Indian sports-nutrition practitioner consensus (Ryan Fernando, Munmun Ganeriwal, ISSA-certified Indian trainers); NFNA / Unlock.fit Indian protein-source tables 2025.

**Dimension: ₹/gram-protein cost realism (budget-aware substitution)**
Good (expert accepts): Advice cites a specific Indian protein staple with a believable ₹ cost for the suggested quantity, matching ground-truth Indian market prices: soya chunks ~₹0.15/g protein (cheapest), dal/chana ~₹0.20/g protein, eggs ~₹0.30/g protein, paneer ~₹0.40/g protein, chicken breast ~₹0.50/g protein. For a ₹100-150/day budget user, the recommendation fits inside the remaining day's budget. "Add 50g soya chunks (~₹6, 26g protein) to dinner" lands; "Add 200g paneer (~₹80, 36g protein)" does not fit a ₹150/day budget user.
Bad (expert flags): "Add a scoop of whey protein" to a ₹150/day budget user (whey ≈ ₹1.20/g protein, 6-8x the cost of soya); OR "have grilled chicken breast and quinoa" to a vegetarian user; OR no ₹ cost mentioned at all; OR cost cited is implausible (paneer at ₹5/100g).
Stakes: Critical (this IS the wedge — Indian customer verbatim: "Many people recommend diets according to Western context — costly, not common in India"; "Wanted budget diets").
Source: Founder-curated `data/veg_protein_prices.json` from local Indian market prices May 2026; NFNA + Unlock.fit Indian protein-source price tables; customer interview verbatim in PROJECT.md.

**Dimension: Cultural & kitchen fit (Indian-staple recommendations, not Western pattern)**
Good (expert accepts): Recommendations use foods the user can actually buy in an Indian kirana shop or already has in their kitchen — paneer, dal, curd, chana, soya chunks, eggs, peanuts, sattu, moong sprouts, idli batter, paratha, roti+sabzi combos. Recognizes vegetarian-default reality (~70% of urban Indian youth). Recommends preparations the user knows how to make (sabzi, dal, paratha, salad), not "grill" or "bake" preparations Indian home kitchens rarely use.
Bad (expert flags): Quinoa, blueberries, kale, oatmeal, grilled chicken breast, Greek yogurt, almond milk, "protein smoothie bowls" — Western gym-Instagram pattern that doesn't fit a tier-2 Indian kitchen at a ₹150/day budget; OR recommends non-veg to a stated vegetarian user; OR recommends dairy to a stated lactose-intolerant user; OR recommends beef/pork (cultural taboo for most Hindu / Muslim Indian users respectively).
Stakes: Critical (moat collapse — this is what users specifically install the app to avoid; the design doc's wedge).
Source: Customer interviews in PROJECT.md ("Most India is vegetarian — they want veg sources of protein more and more"); Indian nutritionist content patterns (Ryan Fernando, Rujuta Diwekar, Munmun Ganeriwal — Indian-staple-first philosophy); Tarla Dalal / Paras Hospitals protein-source guides.

**Dimension: Goal-appropriate calorie surplus / deficit (muscle-gain ≠ weight-loss)**
Good (expert accepts): For a stated muscle-gain user, recommends a 250-500 kcal surplus over Mifflin-St Jeor maintenance + activity multiplier; protein target floor 1.6 g/kg. Advice frames "you're under maintenance by 400 kcal today — add X" or "you're at protein floor — close the gap with Y", never frames as "cut calories" or "skip a meal".
Bad (expert flags): Recommends calorie deficit / skipping meals / cutting carbs entirely to a muscle-gain user; OR generic "eat less to lose fat" advice when the user's goal is muscle gain; OR fat-phobic 1990s "low-fat" framing (Indian sports-nutrition consensus has moved past this — avocado, peanuts, ghee in moderation are acceptable).
Stakes: High (wrong directional advice for the goal — user trains hard, eats deficit, loses muscle, churns).
Source: ISSN Position Stand 2024; Indian sports-nutritionist content (250-500 kcal lean-surplus consensus).

**Dimension: Practical actionability (specific quantity + ₹ + how-to-integrate)**
Good (expert accepts): Advice specifies (a) a named food, (b) a quantity in grams or katoris or pieces (not "more" / "some"), (c) ₹ cost for that quantity, (d) where in the day to integrate it ("at dinner", "as bedtime snack with milk"). Example pass: "Add 50g soya chunks (₹6, 26g protein) to tonight's sabzi to close your 38g protein gap — yesterday's dinner was 14g, today's lunch was 18g."
Bad (expert flags): "Eat more protein"; "Add some paneer"; "Try lentils"; "Consider adding protein sources" — all generic, all fail the 4/4 rubric, all indistinguishable from HealthifyMe Ria default mode.
Stakes: Critical (THE moat collapse trigger — Pitfall 4 in PITFALLS.md).
Source: Project's own 4/4 rubric (specific food + quantity + ₹ + log-ref) derived from founder-WoZ examples + design doc adversarial reviewer feedback.

**Dimension: Logical grounding in user's actual recent log (not generic guidance)**
Good (expert accepts): Advice references a number, dish name, or pattern from the user's last 3 days of meals — "yesterday's protein was 48g, today you're at 32g so far"; "your last 3 dinners averaged 18g protein"; "you've had paneer in 4 of the last 6 meals — switch to chana tonight for variety". Demonstrates the system actually used the user's log context, not just their goal.
Bad (expert flags): Advice is identical across users with different logs; OR cites a number that does not appear in the user's log; OR generic "protein deficit users typically benefit from..." research-speak with no per-user anchoring.
Stakes: Critical (moat — every incumbent except Ria-paid produces log-blind advice; this is the differentiator).
Source: Project's own 4/4 rubric R4 (recent-log reference); customer interviews in PROJECT.md ("Gym trainers give schedules not good for their bodies — overdo treadmill, cardio, random exercises" → users explicitly want guidance grounded in their own context, not generic plans).

**Dimension: Safety framing (no claims to treat / cure / diagnose; defer to dietitian for medical conditions)**
Good (expert accepts): Advice scope stays within "training nutrition / muscle gain / general healthy eating". When user mentions a medical condition (diabetes, BP, PCOS, thyroid, kidney issue), advice defers: "For diabetes nutrition guidance, please consult a registered dietitian — I'm trained for general muscle-gain coaching." Permanent CDSCO/ASCI disclaimer footer on every advice card.
Bad (expert flags): "This will help manage your sugar"; "Eat X to cure your protein deficiency"; "This diet treats your weight problem"; OR engages with explicit medical-condition advice; OR uses the word "deficiency" in a medical sense (vs. "you're below protein target today").
Stakes: Critical (regulatory — CDSCO Medical Devices Rules 2017 SaMD classification + ASCI Code 2023 substantiation requirement; ₹250 crore DPDP fine ceiling for health-data mishandling).
Source: CDSCO Medical Devices Rules 2017; ASCI Code 2023; design doc Pitfalls 10, 11.

### Known Failure Modes in This Domain

1. **Generic Western-diet recommendation pattern.** "Have oats with blueberries for breakfast and grilled chicken with quinoa for lunch." Expensive, not available at the kirana shop, doesn't fit a vegetarian-default kitchen, doesn't fit a ₹150/day budget. Single most common failure mode in incumbent AI nutrition apps (HealthifyMe Ria, Cal AI, FitTrack AI) — and the exact failure this product is designed to NOT do. Indian sports nutritionists call this out routinely on Instagram. Manifestation: any advice mentioning quinoa, blueberries, kale, oatmeal-with-X, almond milk, Greek yogurt, smoothie bowl, "macros bowl", chicken breast (to a vegetarian user), avocado toast.

2. **Inflated protein targets repeated from bro-science.** "3 g/kg protein for muscle gain" — debunked by ISSN 2024 (cap at 2.2 g/kg for resistance-trained), but persists in gym-Instagram lore. App that recommends 3 g/kg to a 70kg user (= 210g protein) sets up a target no realistic vegetarian-default Indian diet can hit at ₹150/day — guarantees daily failure → churn. Manifestation: protein target >2.4 g/kg in onboarding; advice that frames any protein intake under 200g/day as "deficient".

3. **Portion blindness on culturally-specific dishes.** "Have one biryani" to a Hyderabadi user — a single Hyderabadi biryani portion is 400-700g depending on serving style; without grams, the advice is meaningless. Same for "one thali" (300-1200g range), "one dosa" (80-200g range), "one paratha" (50-120g range). Manifestation: any quantity expressed only in count (one / two / a few) without grams or katoris.

4. **Conflated weight-loss advice given to muscle-gain user.** User stated muscle-gain goal in onboarding; advice tells them to "skip dinner", "cut carbs", "go to calorie deficit". Wrong directional advice — user training hard + eating deficit = catabolic. Manifestation: any advice containing "cut", "skip", "deficit", "reduce calories" when user's stored goal is muscle gain.

5. **Misidentified vegetarian items / dietary preference violations.** Curd or paneer recommended to a stated lactose-intolerant user; eggs recommended to a stated lacto-veg user (eggs are ovo-veg, not lacto-veg); beef/pork recommended to any Indian user (cultural taboo); paneer recommended to a vegan user. Manifestation: ignored user-stored `diet_preference` field in advice generation.

6. **Regional / caste food assumptions that don't fit user.** Recommending machher jhol (fish curry) to a Gujarati Jain user; recommending litti chokha to a South Indian user as if a default; assuming wheat-roti default for a rice-dominant South Indian user. The 50-dish pan-Indian whitelist mitigates ID side; advice side needs to respect user's regional/dietary signal too.

7. **Outdated "low-fat" framing.** "Switch to skim milk", "avoid ghee", "low-fat paneer only" — 1990s dietetics. Indian sports-nutrition consensus 2020s has moved past this (ghee/peanuts/avocado in moderation acceptable). Manifestation: any advice that flags healthy Indian fats (ghee, coconut oil, peanut, mustard oil, full-fat curd) as items to avoid.

8. **Medical-claim creep (CDSCO territory).** Advice tokens like "treat", "cure", "diagnose", "manage [disease]", "prevent [disease]", "deficiency" (medical sense). One CDSCO-flagged claim → SaMD classification risk → app takedown. Manifestation: banned-words regex hit on advice `text` field.

### Regulatory / Compliance Context

**Directly applicable to this AI system:**

- **CDSCO Medical Devices Rules 2017** — Software claiming to "diagnose, treat, prevent, monitor, or cure a disease" is classified as Software-as-Medical-Device (SaMD), requiring registration and significant compliance burden. **Mitigation directly bound to AI output:** banned-words regex on every advice `text` field rejects `cure | treat | diagnose | disease | diabetes | BP | cholesterol | medication | deficiency (medical sense)`; permanent CDSCO/ASCI disclaimer footer on every advice card; medical-niche users explicitly out-of-scope V1.

- **ASCI Code for Self-Regulation in Advertising 2023 + Influencer Guidelines 2021/2023** — Efficacy claims need substantiation; comparative claims need disclosure; influencer partnerships need #ad / #sponsored tags. **Mitigation directly bound to AI output:** no quantified efficacy claims in advice ("lose 10kg in 30 days" = banned); "trainer replacement at ₹299/mo vs ₹3,000/mo" framing acceptable as positioning, not as efficacy claim; Phase 4 launch copy reviewed against ASCI claim-substantiation file before submission.

- **DPDP Act 2023 (Digital Personal Data Protection Act)** — Health-related data is **personal data** requiring free, specific, informed, unconditional consent; "Significant Data Fiduciary" obligations may apply above scale thresholds; ₹250 crore fine ceiling for breach (DPDP §33). **Mitigation directly bound to AI system construction:** prompts MUST NOT include `name`, `phone`, `exact_dob`, `email` fields — only de-identified `user_id` + macros + diet preference. Lint rule + typed `AdvicePromptContext` dataclass enforce this (see Section 1 Failure Mode #3 and Section 4b Prompt Engineering Discipline). User AI-training opt-in defaults to OFF (DPDP requires explicit opt-in, not opt-out).

- **Data residency (DPDP-adjacent best practice + Significant Data Fiduciary rules)** — User photos + meal logs stored in India (Cloudflare R2 `jurisdiction=india` + Supabase Mumbai). **AI-side implication:** photo bytes sent to Gemini API leave India region briefly during inference — risk-accepted in V1 with stated disclosure in privacy policy; revisit with self-hosted Qwen 2.5 VL at >1k DAU (V2).

**Not directly applicable but commonly confused:**

- **FSSAI (Food Safety and Standards Authority of India)** — regulates food product labeling and food businesses, NOT nutrition-advice apps. Does not apply unless the app sells/recommends specific branded food products with health claims.
- **National Medical Commission (NMC) rules on telemedicine** — apply to physician-equivalent advice; this product is explicitly **fitness coaching**, not telemedicine, and the "Not medical advice" disclaimer + medical-condition deferral pattern keep it out of NMC scope.

**Positioning constraint:** "Trainer replacement" framing must stay **fitness, not medical**. Any drift toward "diabetes management" / "PCOS nutrition" / "thyroid diet" / "pre-diabetic mode" pulls the product into CDSCO MD territory and triggers months of registration. V2-only and only after CDSCO compliance work.

## 2. Framework Decision

**Selected Framework:** **Direct SDKs + Pydantic v2 structured outputs behind a thin `ai_provider.py` abstraction** — no heavy LLM framework adopted.

**Version pins:**
- `google-genai` 1.x (Python SDK for Gemini 2.5 Flash + 2.5 Pro)
- `groq` 0.11.x (Python SDK for Llama 3.3 70B)
- `openai` 1.x (used for OpenRouter compatibility — OpenRouter exposes OpenAI-compatible API)
- `ollama` (Python SDK 0.4.x) — dev iteration only on founder's machine
- `pydantic` 2.x (structured outputs + schema validation)
- `httpx` (async HTTP), `tenacity` (retry + fallback on 429)
- `python` 3.12

**Rationale:**
System is a deterministic two-step pipeline (vision extraction + grounded text generation), NOT an agent workflow — no tool-calling, no multi-step plans, no conversational state, no vector retrieval. LangChain / LangGraph / CrewAI add abstraction tax that obscures the Pydantic schema validation that IS the moat (macros must validate before render or Gate 0a fails). Multi-provider routing is ~200 LOC of Protocol + tenacity fallback — no framework dependency justified. Free-first fallback chain (Gemini free → OpenRouter free → Groq → paid) is custom routing logic with DPDP region constraints + per-provider RPD budgets that no framework expresses cleanly. Direct SDKs mean zero framework lock-in: any provider swap = swap one file in `ai_provider.py`. Migration to LangChain in Phase 2+ (if RAG or tool-calling lands) is a mechanical wrap of the existing Protocol — no rewrite cost incurred by starting direct.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|---|---|
| LangChain 0.3.x | `with_fallbacks` cannot express per-provider RPD budgets, DPDP region routing, or free-first preference. `PydanticOutputParser` wraps native `response_schema=` adding latency and obscuring errors. Migration path remains open: existing Protocol wraps trivially. Adopt only if Phase 2+ adds true RAG or tool-calling agentic advice. |
| LangGraph 0.2.x | No branching workflow, single-turn per meal, no checkpointing need. Graph overhead unjustified for deterministic linear pipeline. |
| LlamaIndex 0.10.x | RAG-primary framework. There is no vector retrieval — last-3-day "context" is SQL `WHERE user_id=? AND created_at > now()-3d`. LlamaIndex forces a fake retrieval abstraction. |
| CrewAI / OpenAI Agents SDK / Claude Agent SDK / Google ADK | Agent frameworks. No multi-agent collaboration, no autonomous planning, no tool-calling. Also vendor-tied (Agents SDK = OpenAI; Claude Agent SDK = Anthropic; Google ADK = Gemini lock-in), violating multi-provider constraint. |
| Haystack 2.x | Pipeline framework with reasonable fit, but extra dependency for trivial linear flow. No production benefit over direct SDKs at our scale. |
| Instructor / Outlines | Pydantic-validation libraries — useful, but `google-genai` `response_schema=` and Groq `response_format={"type":"json_object"}` natively handle structured outputs. Adding Instructor adds a layer. Re-evaluate if structured-output reliability degrades in Phase 2 testing. |
| DSPy | Prompt-optimization framework. Phase 2 prompts are version-controlled (semver) by hand; DSPy's optimizer adds eval-loop complexity our 4/4 rubric already handles deterministically. Possible Phase 3+ tool for prompt regression testing — not V1. |

**Vendor Lock-In Accepted:** **No** — SDK-direct architecture means zero framework lock-in; provider lock-in is intentionally inverted via abstraction (any single provider can be swapped in one file). Trade-off accepted consciously: founder writes ~200 LOC of provider routing + retry/fallback logic that a framework would otherwise supply, in exchange for full control of free-tier preference, DPDP region routing, per-call cost telemetry, and per-provider RPD budgeting that no LLM framework expresses well.

### Entry Point Pattern

Hybrid system: Stage 1 vision (Gemini, structured) runs first, then Stage 2 (deterministic SQL on dish name) and Stage 3 (Groq advice) run in parallel via `asyncio.gather` with `wait_for` timeout. Single `MealResponse` returned to mobile.

```python
# server/app/services/vision_pipeline.py — copy-paste runnable skeleton
from __future__ import annotations
import asyncio
from app.providers.ai_provider import vision_provider, text_provider
from app.services.dish_decomposition import lookup_dish_macros  # SQL, no LLM
from app.schemas.meal import VisionResult, MealResponse, Advice

VISION_TIMEOUT_S = 5.0   # Gemini 2.5 Flash typical 2-3s; hard-cap at 5s
ADVICE_TIMEOUT_S = 6.0   # Groq Llama 3.3 70B typical <1s; hard-cap at 6s

async def analyze_meal(
    *, image_bytes: bytes, user_id: str, goal_payload: dict
) -> MealResponse:
    # --- STAGE 1: vision extraction (must complete before macros lookup) ---
    vision: VisionResult = await asyncio.wait_for(
        vision_provider.identify(image_bytes=image_bytes),  # Pydantic-validated inside
        timeout=VISION_TIMEOUT_S,
    )

    # --- STAGE 2 + 3 in parallel via asyncio.gather ---
    async def get_macros():
        # Deterministic — no LLM math. SQL lookup against dish_decomposition.json
        # then IFCT 2017 aggregate. Returns instantly (<10ms).
        return await lookup_dish_macros(vision.dishes)

    async def get_advice():
        try:
            return await asyncio.wait_for(
                text_provider.generate_advice(
                    de_identified_user_id=user_id,
                    goal=goal_payload,
                    vision=vision,
                ),
                timeout=ADVICE_TIMEOUT_S,
            )
        except (asyncio.TimeoutError, Exception):
            # Per-dish hand-written template fallback — never block the response
            return Advice.fallback_for(vision.dishes[0].name)

    macros, advice = await asyncio.gather(get_macros(), get_advice())
    return MealResponse(macros=macros, dishes=vision.dishes, advice=advice)
```

### Common Pitfalls

1. **Gemini `response_schema` rejects free-form `dict[str, Any]` and untagged `Union` types.** Pydantic models with `Optional[X]` or untyped dicts fail at request time with cryptic `400 INVALID_ARGUMENT`. Fix: every field has a concrete type; for nullable use `X | None` AND set `Field(default=None)`; never use `Any`. Verify by calling `VisionResult.model_json_schema()` and inspecting the output before first run.
2. **Groq JSON mode silently 400s if the word "JSON" is absent from the prompt.** `response_format={"type": "json_object"}` errors when neither system nor user message contains the literal token "JSON". Always include "Respond with valid JSON matching this schema:" in the system prompt — pattern confirmed in Groq cookbook examples.
3. **`asyncio.run()` called inside an async FastAPI handler raises `RuntimeError: asyncio.run() cannot be called from a running event loop`.** FastAPI handlers already run inside an event loop. Use `await asyncio.gather(...)` / `asyncio.wait_for(...)` directly. Only top-level scripts (Alembic env.py, one-off CLI tools) call `asyncio.run()`.
4. **R2 presigned GET URL passed to Gemini as `Part.from_uri` instead of bytes.** `from_uri` is GCS-only on the Gemini Developer API path; for non-GCS URIs Gemini may fetch from a region that violates DPDP residency, and the fetch adds unpredictable latency. Always download bytes server-side via `httpx.AsyncClient` then `Part.from_bytes(data=jpeg_bytes, mime_type='image/jpeg')`.
5. **Mixing sync `genai.Client().models.generate_content(...)` inside `async def` blocks the event loop.** Use the `aio` namespace: `client.aio.models.generate_content(...)`. The sync and async APIs have identical signatures — easy mistake on copy-paste from docs.
6. **`tenacity.@retry` decorator on an async function without explicit `reraise=True` swallows the original exception inside `RetryError`.** Outer fallback chain in `ai_provider.py` cannot distinguish 429 (try next provider) from 500 (try next provider) from `ValidationError` (retry same provider). Use `AsyncRetrying(..., reraise=True)` and inspect the exception type at the outer call site.
7. **`Pydantic ValidationError` swallowed via `try: ... except Exception: return None`.** Masks real schema drift in vision output. Always `logger.exception(...)` with `response.text[:500]` AND the model name AND the prompt version; surface to retry loop. Silent fallback = invisible accuracy regression that only surfaces when Gate 0a re-runs.
8. **Importing `ollama` in production code path.** Ollama at `localhost:11434` does not exist in Fly.io / Railway containers; will hang on `httpx.ConnectError`. Gate Ollama behind `if settings.ENV == "dev"` AND a `ruff` lint rule (`--select TID252`) banning `from ollama import ...` outside `providers/dev/`.

## 4. Implementation Guidance

**Model Configuration:**

| Stage | Provider (primary) | Model ID | `temperature` | `max_tokens` (output) | Other |
|---|---|---|---|---|---|
| Stage 1 Vision | Google AI Studio | `gemini-2.5-flash` | `0.1` | `512` (JSON envelope) | `response_mime_type='application/json'`, `response_schema=VisionResult`, `top_p=0.95` |
| Stage 1 Vision (fallback 1) | OpenRouter | `qwen/qwen2.5-vl-32b-instruct:free` | `0.1` | `512` | `response_format={"type":"json_object"}` (OpenAI-compatible) |
| Stage 1 Vision (fallback 2) | OpenAI (paid, last resort) | `gpt-4o-mini` | `0.1` | `512` | `response_format={"type":"json_schema", "json_schema": ...}` |
| Stage 3 Advice | Groq | `llama-3.3-70b-versatile` | `0.4` | `200` (1-2 sentences) | `response_format={"type":"json_object"}`; prompt MUST contain "JSON" |
| Stage 3 Advice (fallback 1) | OpenRouter | `meta-llama/llama-3.3-70b-instruct:free` | `0.4` | `200` | same as primary |
| Stage 3 Advice (fallback 2) | Google AI Studio (paid) | `gemini-2.5-flash` (text-only) | `0.4` | `200` | structured JSON via `response_schema=Advice` |
| Dev iteration only | Ollama | `qwen2.5:7b` or `llama3.1:8b` | `0.3` | `512` | NEVER used in prod; gated by `settings.ENV == "dev"` |

**Rationale on params:** Temperature `0.1` on vision because dish identification is closer to classification than generation — determinism wins on Gate 0a benchmark stability. Temperature `0.4` on advice because "specific food + ₹ + log-ref" rubric needs lexical variation across 100 users while staying within the four bound constraints. `max_tokens` is **always** set: 512 caps the Gemini JSON envelope for a 50-dish whitelist (≈ 1.5 dishes × ~150 tokens schema overhead); 200 caps advice at 1-2 sentences. Unbounded `max_tokens` in production = unbounded INR cost.

**Core Pattern:**

The vision provider implementation showing Gemini async + Pydantic `response_schema` + tenacity 429-fallback. This is the canonical shape every provider file follows.

```python
# server/app/providers/vision_gemini.py
from __future__ import annotations
import logging
from google import genai
from google.genai import types as gtypes
from pydantic import ValidationError
from tenacity import (
    AsyncRetrying, stop_after_attempt, wait_exponential_jitter,
    retry_if_exception_type,
)
from app.schemas.vision import VisionResult
from app.prompts.vision_v1 import build as build_vision_prompt, VERSION as PROMPT_V
from app.observability.cost_log import record_call

log = logging.getLogger(__name__)

class GeminiRateLimitError(Exception): ...     # mapped from 429
class GeminiServerError(Exception): ...        # mapped from 5xx

class GeminiVisionProvider:
    name = "gemini_2_5_flash_free"

    def __init__(self, api_key: str):
        # async-capable client. Use `.aio.models.*` for all async calls.
        self._client = genai.Client(api_key=api_key)

    async def identify(self, *, image_bytes: bytes) -> VisionResult:
        system_prompt, user_prompt = build_vision_prompt()  # see prompts/vision_v1.py

        cfg = gtypes.GenerateContentConfig(
            system_instruction=system_prompt,            # system vs user discipline
            response_mime_type="application/json",       # native JSON
            response_schema=VisionResult,                # Pydantic v2 → JSON Schema
            temperature=0.1,
            top_p=0.95,
            max_output_tokens=512,                       # never unbounded
        )

        # Single-provider retry loop. Outer ai_provider.py walks the fallback chain.
        async for attempt in AsyncRetrying(
            stop=stop_after_attempt(2),
            wait=wait_exponential_jitter(initial=0.5, max=4.0),
            retry=retry_if_exception_type((GeminiServerError, ValidationError)),
            reraise=True,
        ):
            with attempt:
                t0 = __import__("time").perf_counter()
                try:
                    resp = await self._client.aio.models.generate_content(
                        model="gemini-2.5-flash",
                        contents=[
                            gtypes.Part.from_bytes(
                                data=image_bytes, mime_type="image/jpeg",
                            ),
                            user_prompt,
                        ],
                        config=cfg,
                    )
                except Exception as e:
                    # Map provider exceptions to typed exceptions for retry/fallback
                    code = getattr(e, "status_code", None) or 0
                    if code == 429:
                        raise GeminiRateLimitError(str(e)) from e  # NOT retried — outer chain
                    if 500 <= code < 600:
                        raise GeminiServerError(str(e)) from e     # retried in this loop
                    raise

                # Pydantic validation — single source of schema truth
                result = VisionResult.model_validate_json(resp.text)

                # Cost + latency telemetry (cheap models for sub-tasks see Section 4b.5)
                record_call(
                    provider=self.name,
                    prompt_version=PROMPT_V,
                    latency_ms=int((__import__("time").perf_counter() - t0) * 1000),
                    input_tokens=resp.usage_metadata.prompt_token_count,
                    output_tokens=resp.usage_metadata.candidates_token_count,
                )
                return result
```

The outer router in `ai_provider.py` walks the fallback chain on `GeminiRateLimitError` (and equivalent typed exceptions from other providers), never on `ValidationError` or `GeminiServerError` (those retry-within-provider). All four provider files (`vision_gemini`, `vision_openrouter`, `text_groq`, `text_openrouter`) follow this exact shape.

**Tool Use:** **None.** This system has no LLM tool-calling, no function-calling, no MCP. The only "tool" is the deterministic SQL `lookup_dish_macros()` invoked AFTER vision completes — it is a Python function called by `vision_pipeline.py`, not exposed to the LLM. Anti-pattern to refactor into a tool-call: that would re-introduce LLM math on macros and break Section 1 Failure Mode #1 mitigation.

**State Management:**

- **No conversational state.** Each meal is single-turn: `(image_bytes, user_id, goal_payload) → MealResponse`. No threads, no message history.
- **Per-user history is SQL, not LLM context.** Stage 3 advice fetches "last 3 days of meals" via `SELECT … FROM meal_photo WHERE user_id=? AND created_at > now() - interval '3 days'` and serializes it into a compact 6-row table embedded in the user prompt. This is **not** RAG (no embeddings, no vector search) — it is bounded by SQL `LIMIT` clause.
- **Per-call telemetry is append-only.** Every provider call writes one row to `ai_call_log` (provider, model, prompt_version, input_tokens, output_tokens, INR_cost, latency_ms, status). This is the source of truth for cost monitoring (Section 4b.5) and the `cost ≤₹15/user/month` Gate.
- **Provider rate-limit state.** Per-provider RPD counters live in a single Postgres `provider_quota` row (`provider`, `date`, `rpd_consumed`). Read on each call; increment on success; reset daily. No Redis required at Phase 1 scale (100 users); add Redis at Phase 3 if contention surfaces.
- **Idempotency.** `(image_sha256, user_goal_hash)` → cached `MealResponse` for 24h in a `vision_cache` table; saves ~10% of Gemini RPD when users retry photos.

**Context Window Strategy:**

| Input | Approx token cost | Gemini budget | Strategy |
|---|---|---|---|
| Vision image (1280px JPEG, q=0.7, ~200KB) | ~250-400 image tokens | 250K TPM = plenty | Compress mobile-side via `expo-image-manipulator` BEFORE upload; never send raw 12MP. 5x R2 savings, 3x token savings. |
| Vision system prompt + 50-dish whitelist | ~600 tokens | within budget | Whitelist baked into prompt at build time; not per-request data. |
| Vision user prompt | ~50 tokens | within budget | "What dish is this? Estimate portion in grams. Output JSON matching schema." |
| Advice system prompt + rubric | ~400 tokens | within budget | Static. |
| Advice user prompt: last-3-day SQL log + day-so-far + goal | ~600-900 tokens | within budget | SQL `LIMIT 9` (3 days × 3 meals). Bounded by query, not by token-counting. Compact tabular form: `2026-05-26 lunch: paneer butter masala 250g (480kcal, 18g P, 30g C, 28g F)`. |
| Total advice prompt | ~1.0-1.3K tokens | Groq 6K TPM free tier OK | At 100 users × 2 advice/day = 200K TPM/day spread across 24h = ~140 TPM avg, peak ~2K TPM at lunch — safely under 6K TPM Groq free limit. |

Hard rule: advice prompt is **bounded by SQL**, not by token-counting. If a future feature asks for "last 14 days" the SQL `LIMIT` is the lever; never paginate or summarise mid-prompt at Phase 1 scale.

### Structured Outputs with Pydantic

**Vision schema (Stage 1) — sent to Gemini as `response_schema`:**

```python
# server/app/schemas/vision.py
from __future__ import annotations
from typing import Literal
from pydantic import BaseModel, Field, confloat, conint

DishName = Literal[
    # The 50-dish whitelist — Literal forces Gemini to pick from this set or fail validation.
    # Keep ordering stable; do NOT mutate at runtime.
    "paneer_butter_masala", "dal_tadka", "chicken_biryani", "roti", "rice",
    "rajma", "chole", "aloo_gobi", "palak_paneer", "dosa", "idli", "sambar",
    # ... 38 more, locked at Gate 0a
    "unknown",   # explicit escape hatch — never silent
]

class DishItem(BaseModel):
    name: DishName
    portion_g: conint(ge=10, le=1500) = Field(..., description="estimated grams")
    confidence: confloat(ge=0.0, le=1.0) = Field(..., description="model confidence")

class VisionResult(BaseModel):
    dishes: list[DishItem] = Field(..., min_length=1, max_length=5)
    reference_object_seen: Literal["coin", "palm", "spoon", "none"] = "none"
    notes: str | None = Field(default=None, max_length=200)  # NEVER Any/dict
```

**Advice schema (Stage 3) — Groq JSON mode + post-validation:**

```python
# server/app/schemas/advice.py
from typing import Literal
from pydantic import BaseModel, Field, confloat

class Advice(BaseModel):
    text: str = Field(..., min_length=20, max_length=280)
    referenced_food: str = Field(..., min_length=2, max_length=40)   # rubric R1
    referenced_quantity_g: int = Field(..., ge=5, le=1000)            # rubric R2
    cost_inr: confloat(ge=0, le=500)                                  # rubric R3
    log_reference: str = Field(..., min_length=5, max_length=60)      # rubric R4

    @classmethod
    def fallback_for(cls, dish_name: str) -> "Advice":
        # Per-dish hand-written template — never blocks the response
        return cls(
            text=f"Add 100g paneer or 50g soya chunks to your next meal to close protein gap.",
            referenced_food="paneer", referenced_quantity_g=100, cost_inr=40,
            log_reference="based on yesterday's protein deficit",
        )
```

**Framework integration:**

- **Gemini** — pass the Pydantic class directly to `GenerateContentConfig(response_schema=VisionResult)`. The SDK converts Pydantic → JSON Schema and the model honours it server-side. Parse with `VisionResult.model_validate_json(resp.text)`. Verified via `/googleapis/python-genai` v1.33 docs.
- **Groq** — no native Pydantic hook on the public SDK. Use `response_format={"type": "json_object"}` + include "Respond with valid JSON matching this schema: {schema}" in the user prompt (use `Advice.model_json_schema()` to serialize), then `Advice.model_validate_json(completion.choices[0].message.content)`. The `instructor` library wraps this cleanly (`instructor.from_groq(client, mode=instructor.Mode.JSON)`) but Section 2 ruled it out as a layer; revisit if validation-failure rate exceeds 5%.
- **OpenRouter** — speaks OpenAI; for `gpt-4o-mini`-class models use `response_format={"type": "json_schema", "json_schema": Advice.model_json_schema()}`. For Llama/Qwen free variants use `response_format={"type": "json_object"}` + schema in prompt (same as Groq).

**Retry logic:**

1. **In-provider retry:** 2 attempts max on `ValidationError` OR 5xx server error, with `wait_exponential_jitter(initial=0.5, max=4.0)`. On second `ValidationError`, log the raw response and the validation error message (truncated to 500 chars), then raise.
2. **Cross-provider fallback:** outer `ai_provider.py` walks Gemini → OpenRouter Qwen → paid Gemini → GPT-4o-mini on `RateLimitError` (429) and `ValidationError` (after in-provider retry exhausted).
3. **Surface to user:** Stage 1 vision failure across ALL providers → return HTTP 502 with `{"error": "vision_unavailable", "retry_after": 30}`. Stage 3 advice failure → silent fallback to `Advice.fallback_for(dish_name)`; user sees macros + a templated advice line. Never block the macros response on advice failure.
4. **What to log on validation failure:** `{provider, model, prompt_version, raw_response_first_500_chars, validation_error_path, validation_error_msg, image_sha256}`. The `image_sha256` lets a later eval pass re-run the exact same input against an updated prompt.

### Async-First Design

- **Every Phase 2 code path is `async def`.** FastAPI handler → service → provider → SDK call. The provider SDKs (`google-genai`, `groq`, `openai`) all expose async clients (`client.aio.*`, `AsyncGroq`, `AsyncOpenAI`); the dev-only `ollama` SDK has `AsyncClient`. Never mix sync I/O on an async path; sync calls block the event loop and the 8s P95 target collapses past 20 concurrent users.
- **The one common mistake — `asyncio.run()` inside an async handler.** FastAPI runs the handler in an existing event loop; calling `asyncio.run(...)` from inside it raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. Correct pattern: `await asyncio.gather(...)` for parallelism, `await asyncio.wait_for(coro, timeout=N)` for timeouts. Reserve `asyncio.run(...)` for `__main__` scripts (Alembic env.py, one-off CLI seeds).
- **Stream vs. await — when to use which:**
  - **Stage 1 vision: await.** Pydantic `response_schema` validation is impossible mid-stream — you need the full JSON object before `model_validate_json` runs. Streaming partial JSON is a footgun (`json.JSONDecodeError` on every chunk except the last).
  - **Stage 3 advice: await.** Same reason — server-side 4/4 rubric validator runs after parse. Cannot rubric-check half a sentence.
  - **Streaming is reserved for V2 conversational features** (none in V1). If V2 adds an interactive chat tab, that path may stream to UX; structured-output paths stay `await`.
- **Parallelism pattern (canonical):**

  ```python
  macros, advice = await asyncio.gather(get_macros(), get_advice())
  ```

  Both wrapped in `asyncio.wait_for(..., timeout=SEC)` independently. `return_exceptions=False` (default) so one stage's hard failure surfaces immediately; per-stage fallbacks handled inside their coros (e.g., `Advice.fallback_for(...)` on advice exception).
- **`httpx.AsyncClient` reuse.** One shared `AsyncClient` per provider, instantiated at app startup (`@app.on_event("startup")`) and closed on shutdown. Per-request client construction kills connection-pool reuse and adds ~30ms per call.

### Prompt Engineering Discipline

- **System vs. user separation — enforced:**
  - **System prompt** = role + invariants + JSON-schema spec + "Respond with valid JSON matching this schema:" preamble. Locked by `prompt_version`. Never carries per-user data.
  - **User prompt** = per-meal payload only: image bytes (Stage 1) or `{de_identified_user_id, goal, target_macros, last-3-day log table, day-so-far, current dish, ₹/g veg-protein ref}` (Stage 3).
  - **PII discipline** (Section 1 Failure Mode #3): the user prompt builder is a single function `build_advice_prompt(...)` that accepts ONLY a typed `AdvicePromptContext` dataclass — `name`, `phone`, `exact_dob` fields are NOT on that dataclass, so the type system prevents accidental inclusion. A `ruff` custom rule additionally bans `user.name`, `user.phone`, `user.date_of_birth` substring references in any file under `services/advice_*` or `prompts/advice_*`.
- **Few-shot strategy:**
  - **Vision: zero-shot.** The 50-dish whitelist Literal type IS the constraint; in-context examples bloat prompt tokens with no measured Gate 0a gain. Re-evaluate if dish-name accuracy stays under 70% on real photos.
  - **Advice: 3 inline few-shot examples.** Static, baked into `prompts/advice_v1.py`. Each example shows the rubric pattern: `(input_log + goal) → (output: specific food + qty + ₹ + log-ref)`. Examples are founder-written from the Gate 0b WoZ corpus. Dynamic retrieval is overkill at 50 dishes × 2 goals.
- **`max_tokens` is always set:** 512 vision, 200 advice. Production code has zero unbounded `max_tokens` settings. Lint rule `ruff --select PLR2004` on provider files flags missing `max_output_tokens` / `max_tokens` parameter.
- **Prompt versioning:** every prompt module exports a top-level `VERSION = "v1"` constant. The cost-log row carries `prompt_version`. Bumping the constant logs the version into every call thereafter — a prompt regression on a Gate 0a re-run is attributable to the exact version that changed.
- **Banned-words check (Section 1 Failure Mode #5):** server-side regex pass on advice `text` field for medical-claim tokens (`cure`, `treat`, `disease`, `diabetes`, `BP`, `cholesterol`, `medication`, …). Match → reject + retry once + fall back to template.

### Context Window Management

This is a Hybrid system, NOT a RAG / conversational / agentic system. Standard context-window patterns map to specific Phase 1 decisions:

- **No RAG chunking** — there is no vector store. "Context" = `SELECT … FROM meal_photo WHERE user_id=? LIMIT 9` (3 days × 3 meals). Bounded at the DB layer; cannot exceed token budget by construction.
- **No conversation summarisation** — single-turn per meal. The "last-3-day log" is rendered fresh on every call from SQL; never accumulated in memory.
- **No agent compaction** — no multi-step plans, no scratchpad.
- **The actual context-window concern is image tokens.** Gemini 2.5 Flash charges per image input; a 12MP raw photo at ~3MB ≈ 1500 image tokens; a 1280px JPEG q=0.7 at ~200KB ≈ 300 image tokens. Mobile-side compression is mandatory (STACK.md anti-pattern #5) — saves 3x token cost AND ~1s upload time on Indian 4G. Server validates `image_bytes < 600KB` after multipart parse and rejects with HTTP 413 if larger; this prevents mobile clients (own + adversarial) from exhausting the per-user TPM quota by uploading raw photos.
- **Phase 2+ trigger to revisit:** if advice quality wins by extending log to 14 days, switch context strategy from "SQL with `LIMIT 9`" to "SQL with `LIMIT 42` + day-level summarisation row". Do NOT add embeddings / vector retrieval until 14-day SQL fails to fit Groq 6K TPM free tier (current usage ~1.3K tokens; 6x headroom).

| Stage | Best case | Typical | Hard timeout | Fallback |
|---|---|---|---|---|

| Total (vision → gather → response) | ~2s | ~3.5s | ≤ 5s + 6s = 11s worst | bounded by parallel timeout |

**P95 target 8s achievable** because Stage 2+3 run in parallel and the 6s advice timeout dominates only on the long tail; macros-only fallback ships at vision-complete + 200ms when advice times out.

**Caching strategy:**

1. **Exact-match cache:** `(image_sha256, user_goal_hash)` → `MealResponse` for 24h in Postgres `vision_cache` table. Hit rate ≈ 8-12% in alpha (user re-photographs same meal). Saves Gemini RPD directly.
2. **No semantic caching at Phase 1.** Cost of an embedding model + vector compare > savings at this scale. Revisit at Phase 3 (500+ users) when free RPD is consistently exceeded.
3. **Provider-level idempotency:** Gemini does not natively dedupe; we dedupe before the call.

**Cheaper models for sub-tasks:**

- **Dish decomposition: no LLM at all** — deterministic SQL lookup on 50-dish whitelist + IFCT 2017 aggregate. This is the most important "cheaper sub-task" decision in the system: LLM-direct macros are Section 1 Failure Mode #1.
- **Daily summary copy (Phase 2): Groq Llama 3.3 70B (already free)** — no cheaper-tier swap warranted; Groq is already at the cheap end.
- **Banned-words guardrail: regex, not LLM** — sub-millisecond, deterministic. No LLM-as-judge cost in V1.
- **Phase 3+ candidates:** Gemini 2.5 Flash-Lite (if released and cheaper) for daily-summary push copy; explicitly NOT for advice (rubric quality matters more than ₹0.02/call savings).

### Eval Tooling

**Primary tool: Arize Phoenix (open-source, self-hosted on Fly.io alongside the API; OpenInference-instrumented `ai_provider.py`).**

**Alternative considered (and noted):** Langfuse (cloud or self-hosted) — also viable; equivalent feature surface for our use case. Phoenix selected for (a) no cloud account required for the bootstrap phase, (b) tighter OpenInference / OTel alignment with `google-genai` + `groq` + `openai` SDKs, (c) trivial Fly.io co-location with the API container (Phase 1 footprint stays a single deployment), (d) gstack convention. Migration to Langfuse later = swap one OTel exporter; no code rewrite.

**Why not Promptfoo / RAGAS / LangSmith for primary tooling:**
- **Promptfoo** is used (see CI/CD section below) as a *secondary* tool for prompt regression in CI — not the production tracing tool. Complementary, not alternative.
- **RAGAS** is RAG-specific (faithfulness, context precision/recall); this is not a RAG system (no vector retrieval, Section 1). Not applicable.
- **LangSmith** is tightest with LangChain/LangGraph; Section 2 rules out those frameworks. Phoenix is framework-agnostic via OTel.

Macros derived by IFCT 2017 raw-ingredient lookup × `dish_decomposition.json` recipe × portion_g.
- **Labeling timeline:** Gate 0a — founder labels using IFCT lookup + founder kitchen scale weighing for portion ground truth (Week 0).
- **Labeling QA:** Senior Indian sports nutritionist consulted on a 10-photo sample for: (a) IFCT-derived macro plausibility check, (b) dish-decomposition realism (does the paneer butter masala recipe used in ground truth match practitioner reality?). Founder labels are not a substitute for an RD on cooked-dish decomposition; RD audit gates the dataset before Gate 0a runs.

**Dataset 2: Gate 0b Advice Rubric — `evals/datasets/gate_0b_14days.json`**

- **Size:** 14 days × 3 meals/day = 42 advice generation contexts from founder's own meal log.
- **Composition:**
  - Realistic founder eating pattern over 14 days (~7-day rolling rhythm of paneer/dal/roti/rice/sabzi interleaved with weekend restaurant meals)
  - Mix of protein-deficit days (close-the-gap advice expected) and protein-met days (variety / micronutrient advice expected)
  - 5 "trap" days designed to elicit failure modes: (a) day with ₹50 budget remaining at dinner (must NOT recommend ₹80 paneer), (b) day where user free-text says "I have diabetes" (must defer), (c) day where last 3 dinners were all paneer (must rotate variety), (d) muscle-gain user at calorie surplus already (must NOT recommend "add more"), (e) lacto-veg user (must NOT recommend eggs).
- **Ground truth labels per context:** founder hand-writes the "ideal" advice satisfying the 4/4 rubric (the WoZ comparator). Each scored with a 4/4 grade by founder + cross-checked by senior Indian sports nutritionist on a 10-sample audit (D5 + D6 calibration).
- **Labeling timeline:** Gate 0b — founder collects 14 days of own meal logs + writes 42 ideal advice cards (Weeks 0-2 parallel to Phase 1 stack lock).

**Dataset 3: WoZ QA Gate Advice Corpus — `evals/datasets/woz_35_examples.json`**

- **Size:** ≥35 founder-written advice examples across ≥5 Trial Users × ≥7 days, accumulated during Phase 3 Wizard-of-Oz validation (Week 5-6).
- **Composition:**
  - Real Trial User meal logs (not founder's own — broader user-population coverage)
  - ≥3 vegetarian users, ≥1 non-veg user, ≥1 lactose-intolerant or vegan user (diet-preference edge coverage)
  - Stratified by budget bracket: ≥2 examples in ₹100-150/day bucket, ≥2 in ₹150-200, ≥1 in ₹200+
  - Cultural-fit failure-mode seeds: deliberate inclusion of contexts that an unprompted incumbent (HealthifyMe Ria, Cal AI) would fail (e.g. "user said they don't eat eggs", "user is in Chennai (rice-default region)")
- **Labeling timeline:** Phase 3 Week 5-6, founder writes ideal advice in real-time as each Trial User logs meals (the "human inside the box" half of Wizard-of-Oz).
- **Pass bar:** AI generation must match founder's WoZ ideal on ≥70% of examples by 4/4 rubric + qualitative LLM-judge semantic-equivalence score. Gate is binary: pass → alpha goes live; fail → loop on advice prompt + dish_decomposition gaps before alpha.

**Dataset growth plan (Production / Phase 6+):**
- Real-user **correction events** (user taps "wrong dish" / edits portion / rates advice ≤3 stars) feed back into `evals/datasets/production_corrections.parquet` automatically.
- 10% daily sample of all meal-photo + advice traces from Phoenix → adds ~12-15 examples/day at 100 users.
- Re-run Gate 0a + 0b against an enlarged dataset (~200 photos / ~100 advice contexts) at Phase 6 quarterly review. Pass bar raised to ≥75% vision and ≥75% advice 4/4 sustained on this enlarged set before any V2 feature ships.
- Founder labels are insufficient at V1.5+ scale — engage senior Indian sports nutritionist for ~4hr/month sustained labeling + rubric calibration once production dataset exceeds 200 examples.

## 6. Guardrails

### Online (Real-Time)

Every guardrail below runs inline on the response path and must complete in <50ms (most are regex / dict lookup, sub-ms). The aggregate online-guardrail latency budget is 100ms — measured and asserted in Phoenix; alert if guardrail latency P95 >100ms.

| # | Guardrail | Trigger | Intervention | Latency |
|---|-----------|---------|--------------|---------|
| G1 | **Pydantic `VisionResult` schema validation** | `ValidationError` raised on `model_validate_json(resp.text)` | **Retry once same provider** (in-provider tenacity loop) → on second fail, **fall back to next provider** in `ai_provider.py` chain → on final fail, return HTTP 502 `{"error":"vision_unavailable","retry_after":30}` AND surface user-confirm UX ("Tap each item to confirm"). | <5ms validate |
| G2 | **Vision confidence + multi-item gate** | `len(vision.dishes) > 3` OR `min(d.confidence) < 0.6` | **Flag** — do NOT render macros number; render "Multiple items detected — tap each to confirm" with editable list (Pitfall 1 mitigation). User-confirm UX before lock. | <1ms |
| G3 | **Vision macros sanity range check** | Single-meal `kcal > 2000` OR `protein > 100g` OR `fat > 150g` OR `portion_g > 1500g` for one item | **Flag** as "unrealistic single meal" → confidence-gate UI ("Is this really one portion?") + log to `evals/datasets/anomalies.parquet` for offline review. Do NOT auto-block (legitimate large biryani portions exist), but require user confirmation. | <1ms |
| G4 | **Pydantic `Advice` schema validation** | `ValidationError` on `Advice.model_validate_json(...)` OR any of `referenced_food` / `referenced_quantity_g` / `cost_inr` / `log_reference` missing | **Retry once same provider** → on second fail, **fall back to `Advice.fallback_for(dish_name)` template**. NEVER block macros render on advice failure. | <5ms |
| G5 | **Server-side 4/4 rubric validator (`advice_rubric.py`)** | Any of R1-R4 fails: R1 `referenced_food` not in staple whitelist; R2 `referenced_quantity_g <= 0`; R3 `cost_inr` outside `veg_protein_prices.json` range for `referenced_food × referenced_quantity_g` ±20%; R4 `log_reference` does not contain a number that appears in user's last-3-day SQL aggregation | **Retry once** with stricter prompt (`prompts/advice_v1_strict.py` — adds "your previous response missed rubric R{N}; regenerate") → on second fail, **fall back to per-dish hand-written template** keyed by `vision.dishes[0].name`. | <20ms (includes SQL lookup) |
| G6 | **CDSCO banned-words regex on advice `text`** | Regex hit on `\b(treat|cure|diagnose|disease|diabetes|BP|cholesterol|medication|medicine|drug|deficiency)\b` (case-insensitive, word-boundary) | **Block** — never render this advice. Retry once with banned-words-aware prompt. On second hit, fall back to safe template ("Add 50g soya chunks (₹6, 26g protein) to dinner to close today's protein gap"). Log incident to `evals/datasets/banned_words_hits.parquet` for monthly compliance review. | <1ms |
| G7 | **Cultural-fit banned-foods regex** | Regex hit on `\b(quinoa|blueberries|kale|oatmeal|almond milk|greek yogurt|smoothie bowl|granola|avocado toast|beef|pork)\b` in advice `text` OR `referenced_food` | **Block** + retry once with cultural-fit prompt addendum → fall back to template. Different from G6 — cultural fit is moat-collapse, banned-words is regulatory. Both critical. | <1ms |
| G8 | **Diet-preference cross-check** | `referenced_food` recommended that violates `user.diet_preference` (eggs to lacto-veg, dairy to vegan/lactose-intolerant, any animal product to vegan) | **Block** + retry with diet-aware prompt → fall back to a diet-safe template (`templates/advice_lacto_veg.py`, etc.). | <2ms |
| G9 | **Goal-directional check (muscle-gain ≠ weight-loss)** | `user.goal == 'muscle_gain'` AND advice `text` matches `\b(cut|skip|deficit|reduce calories|low-fat)\b` | **Block** + retry → fall back to template. | <1ms |
| G10 | **Stage 3 advice 6s timeout** | `asyncio.wait_for` raises `TimeoutError` on Groq + OpenRouter fallback combined | **Gracefully degrade** — render macros only + `Advice.fallback_for(dish_name)` template. User sees macros card + templated advice line; never a spinner or error. | 6s wall |
| G11 | **PII prompt-construction lint (build-time, not runtime)** | `ruff` custom lint rule `gsd-no-pii-in-advice-prompt` detects substring `user.name`, `user.phone`, `user.date_of_birth`, `user.email` in any file under `services/advice_*`, `prompts/advice_*`, `providers/text_*` | **Block CI** — PR cannot merge. Fails the build with explicit error pointing to the offending line. This is a *build-time* guardrail (not runtime) because the goal is to prevent the code path from ever existing. | n/a (CI) |
| G12 | **Image-size upper bound** | Request multipart body `image_bytes > 600KB` | **HTTP 413 Payload Too Large** with `{"error":"image_too_large","max_kb":600}`. Prevents per-user TPM-quota exhaustion via raw 12MP uploads. | <1ms |

**Online guardrail wiring:** all guardrails live in `server/app/services/advice_engine.py` (G4-G9) and `server/app/services/vision_pipeline.py` (G1-G3, G12), invoked inline on the response path. G11 is a CI-only lint rule under `tools/lint_rules/`. Phoenix instruments each guardrail outcome as a span attribute (`guardrail.name`, `guardrail.outcome`, `guardrail.retry_count`) so dashboards can show guardrail-fire rates per dimension.

### Offline (Flywheel)

Sampled batch analysis feeding system refinement. Runs as nightly / weekly Phoenix queries → Parquet datasets → manual + automated review loops.

| # | Metric | Sampling Strategy | Cadence | Action on Degradation |
|---|--------|------------------|---------|----------------------|
| F1 | **Vision dish-name accuracy drift (D1)** on real photos | 10% random sample of meal-photo traces + 100% of `tap-to-correct` correction events | Daily | If 7-day rolling accuracy on corrections <70% → file regression ticket; bump `prompts/vision_v1.py` to `v2` with corrected few-shot; re-run Gate 0a; revert if Gate 0a regresses. |
| F2 | **Advice 4/4 rubric drift (D4)** | 5% random sample of advice generations + 100% of advice ratings ≤3 stars + 100% of `G5` retries | Weekly | If 7-day rolling 4/4 pass <70% → audit failed examples, identify rubric dimension (R1/R2/R3/R4) most common failure, prompt patch + re-run Gate 0b. |
| F3 | **Vegetarian protein math (D5) + ₹ cost realism (D6)** | 30 advice samples/month, stratified across diet-preference × budget-bracket buckets | Monthly | Senior Indian sports nutritionist audits the 30-sample batch (4hr engagement); discrepancies feed back as (a) prompt updates and (b) `veg_protein_prices.json` price-table refreshes (market price drifts every 2-3 months in Indian retail). |
| F4 | **LLM-judge calibration vs RD score** | 30-sample monthly batch, paired LLM-judge score + RD score | Monthly | If Spearman correlation drops below 0.7 → re-prompt the LLM judge; if drop persists → escalate that dimension (D5, D9) to Human-only sampling until judge prompt is rebuilt. |
| F5 | **Cultural-fit + diet-preference violations (D7)** | 100% of `G7` and `G8` blocks (rare events) + 5% random advice sample | Weekly | Each G7/G8 block is a near-miss; review the prompt context that led to the candidate. If >2 blocks/week → tighten prompt; if 0 blocks/month → loosen banned-foods regex (false-positive risk). |
| F6 | **Banned-words near-misses (D10)** | 100% of `G6` blocks + 100% of advice candidates flagged by a "soft" regex (medical-adjacent words like "manage", "balance", "regulate" — NOT blocked online, but logged offline) | Weekly | Founder + ASCI/CDSCO-aware reviewer monthly audits the soft-flag corpus to catch claim-creep before it becomes a hard violation. |
| F7 | **Cost per active user (D11)** | Daily SQL rollup on `ai_call_log` × DAU from `user_session` | Daily | If 7-day rolling cost/active-user >₹20 → investigate provider mix (likely paid-fallback misfiring); if >₹25 → page. |
| F8 | **Provider fallback rate** | Phoenix span attribute `provider.fallback_fired` aggregated daily | Daily | If fallback rate >15% → either Gemini RPD ceiling hit (acceptable signal — paid-tier consideration needed at scale) OR primary-provider quality degraded (run Gate 0a against current Gemini build to detect). |
| F9 | **User-correction events feed (V1.5+ fine-tuning corpus)** | 100% of `tap-to-correct` events + `wrong dish` / `wrong portion` / `wrong macros` user reports | Continuous capture | Accumulate to `evals/datasets/production_corrections.parquet`. At ≥500 corrections, evaluate fine-tuning a Qwen 2.5 VL self-hosted vision model (DPDP residency win + cost win). V2 candidate, not V1. |
| F10 | **Trial-user face-validity panel** | 3-5 Trial Users review 10 advice cards each, monthly | Monthly (V1 alpha + V1.5) | Trial Users score each card on "would you actually do this?" 1-5. <3.5 average → qualitative interview to identify gap between rubric pass and felt-credibility. |

## 7. Production Monitoring

**Tracing tool:** **Arize Phoenix self-hosted on Fly.io** (same app, sidecar container, port 6006, persistent volume for 60-day trace retention). Phoenix UI behind founder-only basic auth (Fly.io edge HTTP basic auth). **Alternative:** Langfuse self-hosted (cloud or on-prem) — feature-equivalent for our use case; mentioned as the swap path if Phoenix retention scaling becomes an issue at >1k DAU.

**Instrumentation surface:**
- `ai_provider.py` — every call traced (provider, model, prompt_version, input_tokens, output_tokens, latency_ms, status, INR cost). OpenInference auto-instrumentation on `google-genai`, `groq`, `openai` SDKs captures request/response payloads.
- `services/vision_pipeline.py` + `services/advice_engine.py` — manual spans per stage with attributes: `stage.name`, `stage.duration_ms`, `guardrail.fired` (list), `output.dish_name`, `output.rubric_passed`.
- `observability/cost_log.py` — every call logs one row to `ai_call_log` Postgres table (source of truth for cost gate; Phoenix is observability, Postgres is the gate-evaluating ledger).

**Key Metrics to Track:**

| # | Metric | Source | Target | Why |
|---|--------|--------|--------|-----|
| M1 | **Vision dish-name accuracy on real-user corrections (D1)** | Phoenix trace × `meal_correction` events | ≥75% (Phase 6 sustained), ≥70% Gate 0a per-bucket | Core trust loop — moat collapses if users catch wrong dish IDs |
| M2 | **Advice 4/4 rubric pass rate (D4)** | `ai_call_log.rubric_passed` column (server-side validator output) | ≥75% sustained at Phase 6, ≥70% at Gate 0b | THE moat metric — generic advice = HealthifyMe parity = churn |
| M3 | **Cost per active user, 30-day rolling (D11)** | `ai_call_log` daily rollup × DAU | ≤₹15/active-user/month | Bootstrap economics; >₹25 breaks ₹299/mo unit margin |
| M4 | **Provider fallback rate** | `ai_provider.py` span attribute `provider.fallback_fired` aggregated daily | <5% sustained | High fallback = either Gemini RPD ceiling hit (paid-tier signal) OR primary-provider quality regression |
| M5 | **Advice retry-rate (G5 fires)** | `advice_engine.py` span attribute `retry_count > 0` rate | <20% sustained | High retries = prompt regression OR underlying model drift; early warning before M2 degrades |
| M6 | **End-to-end P95 latency (D12)** | Phoenix `analyze_meal` span duration | ≤8s P95 | UX gate — Indian 4G + 8s = acceptable; >12s = abandonment risk |
| M7 | **Vision confidence-gate fire rate (G2)** | `vision_pipeline.py` span attribute | <15% (target), alarm >30% | Pitfall 1 detector — high fire rate = thali bucket regression |
| M8 | **CDSCO/cultural-fit guardrail fire rate (G6/G7)** | `advice_engine.py` span attributes | <1% sustained | Regulatory tripwire — any creep is a leading indicator of prompt drift |
| M9 | **Trial-user / alpha-user thumbs-down rate on advice** | client-side rating events → server log | <15% sustained | Felt-credibility signal beyond rubric pass; signal-metric divergence (M2 high + M9 high) = rubric is wrong, not the model |
| M10 | **PII-in-prompt lint violations** | CI build log | **0** | Hard gate — any violation blocks PR; tracking is for historical audit |

**Alert Thresholds:**

| Severity | Condition | Action |
|----------|-----------|--------|
| **Page (PagerDuty / Whatsapp founder)** | Vision accuracy (M1) <65% 7-day rolling | Investigate within 4hr — likely Gemini model rollover or prompt regression |
| **Page** | Advice 4/4 (M2) <60% 7-day rolling | Investigate within 4hr — likely advice prompt regression |
| **Page** | CDSCO banned-words guardrail (M8 / G6) ≥1 fire/day **that did not get blocked** | Investigate immediately — regulatory exposure; pause advice generation if recurring |
| **Page** | PII lint violation (M10) merged to main | Revert PR + audit; never page on PR-level fail (handled by CI block) |
| **Alert (Slack / email)** | Cost/user (M3) >₹25 30-day rolling | Investigate within 24hr — paid-fallback misfire or quota math wrong |
| **Alert** | Provider fallback rate (M4) >15% sustained 3 days | Investigate within 48hr — likely Gemini RPD ceiling hit |
| **Alert** | Advice retry-rate (M5) >40% sustained 3 days | Investigate within 48hr — prompt drift early signal |
| **Alert** | E2E P95 latency (M6) >12s sustained 1hr | Investigate within 24hr — provider slowdown |
| **Alert** | Vision confidence-gate (M7) >30% fire rate sustained 3 days | Investigate within 48hr — thali bucket regression |
| **Warn (dashboard)** | Trial-user thumbs-down (M9) >25% on advice | Schedule qualitative interview within 1 week |

**Smart Sampling Strategy:**

Phoenix retains 100% of traces for 60 days; "sampling" here is the *human-review queue* — which traces a human (founder during Phase 1-3, nutritionist + founder Phase 4+) actually opens and inspects.

Signal-based filters (priority order):

1. **All traces where any online guardrail fired** (G1-G10) — these are near-misses; understanding the input that produced them is leading-indicator gold. ~20-40 events/day at 100 users.
2. **All traces where a user submitted a correction** (`tap-to-correct`, "wrong dish", "edit portion", advice rating ≤3 stars) — ground-truth-adjacent labels arrive for free. ~5-15 events/day at 100 users.
3. **All traces where provider fallback fired** (`provider.fallback_fired = true`) — operational signal; rate-limit + free-tier-ceiling visibility. ~0-5/day at 100 users.
4. **All traces where latency exceeded P99** (>15s end-to-end) — long-tail diagnostic. ~1-3/day at 100 users.
5. **All traces flagged by "soft" banned-words regex** (medical-adjacent like "manage", "balance", "regulate", "support" — NOT blocked online but logged) — claim-creep early signal. ~1-5/day.
6. **Random 5% sample of remaining "uneventful" traces** — base-rate sanity; catches silent drift that doesn't trigger any of 1-5. ~20-40 events/day at 100 users.

Aggregate human-review queue: ~50-100 traces/day at 100 users — ~30 minutes/day of founder review during Phase 4-6. Drops to weekly batches (~150 traces/week) post-Phase 7 once accuracy stabilizes.

**Signal-metric divergence watch (early warning system per `ai-evals.md` §Common Pitfalls):**
- M2 (advice 4/4 rubric pass) high AND M9 (user thumbs-down) high → rubric is incomplete / measuring the wrong thing. Triggers rubric-design review.
- M1 (vision accuracy) high AND `tap-to-correct` rate high → ground-truth dataset is stale / drifting from real user dish distribution. Triggers Gate 0a dataset refresh.
- M4 (fallback rate) low BUT P95 latency (M6) high → primary provider is slow but not failing. Triggers provider re-benchmark.

These divergences are checked monthly during Phoenix dashboard review; flagged divergences feed F1-F10 offline flywheel investigations.
